# Atelier — Formula Studio

A working customer-and-staff demo built with React, Node.js/Express and Prisma. SQLite keeps local setup simple; no database service account is required. This is a mobile-friendly website, not an iOS/Android native app.

## Quick start

Use Node.js 22 or 24 LTS with npm. Keep the downloaded files in the directory structure below.

```bash
npm install
npm run setup
npm run dev
```

Open **http://localhost:5173** for customers and **http://localhost:5173/staff** for staff.

The local demo staff access key is **demo-staff**. A fictional customer and pending formula are seeded for exploration. Running setup again does not erase your records or overwrite the catalog.

Optional: copy `.env.example` to `.env` to configure the staff key, public app address and SMTP. If you set STAFF_KEY, enter that value instead of demo-staff. Restart the Node server after environment changes.

## Demo walkthrough

1. Open the customer screen and enter fictional contact details.
2. Select Bergamot and Neroli; assign 60% and 40%.
3. Choose Eau de parfum (20%), name the product and submit.
4. Open `/staff`, enter `demo-staff`, and select **Refine** for the submission.
5. Adjust the name, blend or strength. Inspect sample and full-size quantities.
6. Select **Approve & save formula**. The recipe is now immutable.
7. Reopen the approved formula to copy the label name, print its QR card or open the reorder page.
8. Check **Email outbox** for the thank-you message and product/reorder URL. Without SMTP nothing is sent externally.
9. Open that URL, choose a size and request another bottle.
10. In **Reorders**, change the request from NEW to IN_PROGRESS or COMPLETED.
11. In **Administration**, edit an ingredient name or strength, save, then reopen the approved formula: its original recipe is preserved.
12. Mark an ingredient unavailable. Existing saved recipes remain unchanged, but their reorder requests are blocked until the ingredient becomes available again.

The staff workspace refreshes every six seconds. Customers and formulas are searchable. The Customers view links each profile to its saved and pending formulas. Matching email addresses group submissions under an existing customer without allowing an unauthenticated submission to overwrite that profile's contact details.

## Calculation assumptions

This demo assumes a fragrance product calculated **by volume in millilitres**:

- Ingredient percentages are percentages of the fragrance concentrate and must total 100%.
- Strength is the percentage of the final product that is concentrate.
- Remaining volume is base/diluent.
- Every selected ingredient must have a positive percentage.
- A default 2 ml test sample is configurable in Administration.

For a 50 ml product at 20% strength with a 60/40 blend:

| Component | Calculation      | Quantity |
| --------- | ---------------- | -------- |
| Bergamot  | 50 × 0.20 × 0.60 | 6 ml     |
| Neroli    | 50 × 0.20 × 0.40 | 4 ml     |
| Base      | 50 × 0.80        | 40 ml    |

The 2 ml sample contains 0.24 ml Bergamot, 0.16 ml Neroli and 1.60 ml base. The display rounds to 0.001 ml. No gram conversions, density corrections, manufacturing tolerances or chemical safety constraints are implemented. These example calculations must be confirmed before real production.

## Formula history and availability

Approval stores a JSON snapshot of ingredient IDs, names, families, colours, percentages, strength name/concentration and sample size inside the Formula record. Staff cannot overwrite an approved formula through the API. Submit a new formula to create a revision; explicit revision lineage is not implemented.

Ingredient and strength edits affect new approvals, not approved records. Reordering checks ingredient availability using stable IDs, and uses the currently available sizes and prices. Each reorder stores its own size and price snapshot. Currency is USD for this demo. There is no inventory quantity tracking.

## QR codes and testing on a phone

QR images are generated by the Node backend, without an external QR service. Administration shows the creation-form code; approved formulas show their own product code.

For a phone on the same Wi-Fi network, set APP_URL to `http://YOUR_COMPUTER_LAN_IP:5173`, restart the backend, and allow access to the Vite port. Open the same address on the desktop when testing links. Vite binds to all interfaces in development. `localhost` on a phone refers to the phone, so the default QR address will not reach your computer.

Product links use random 192-bit tokens. Treat them as private bearer links: anyone holding the link can view the saved product and submit a reorder request. The public product response does not expose customer contact details. There is no customer password or email ownership verification in this demo.

## Email

With SMTP_HOST empty, approval creates a DEMO outbox entry only. With SMTP configured, approval tries to send a plain-text thank-you email and records SENT or FAILED. Staff can inspect failures in the outbox. Automatic retries, provider webhooks, bounce handling and inbox-delivery guarantees are not included. Only connect SMTP when you intend to send real messages. Staff receives reorder requests in the dashboard; staff notification emails are not implemented.

## Build and run

```bash
npm run build
npm start
```

This serves the compiled React app and API together at **http://localhost:3001**. For this mode set APP_URL to `http://localhost:3001`, or to the real HTTPS domain when hosted.

This Node/Prisma server requires a Node hosting environment with a **persistent disk** for `prisma/demo.db`. It is not a static-hosting-only project. Do not use an ephemeral SQLite file in a serverless deployment. A later production release can migrate the Prisma datasource to PostgreSQL with a proper migration and data-transfer plan.

## Verification

```bash
npm test
npm run build
```

To run the API integration test, start the server in another terminal, then:

```bash
npm run test:integration
```

Run integration tests only against your disposable local demo database with SMTP disabled. They create temporary records, modify the catalog to verify snapshot protection, then restore the original catalog and remove their own records. Stop other edits during the test. If you use a custom STAFF_KEY, configure the same value for the test process.

Tests cover total-volume calculations, invalid percentages, duplicate ingredients, staff access protection, submission/approval, immutable snapshots after catalog changes, email capture, QR output, reordering, reorder status and ingredient unavailability. Production compilation and these tests passed during creation. Cloud browser preview could not connect to the local server, so interactive visual, mobile-device and print-dialog checks remain manual.

## Demo boundaries

Included: customer creation form, staff refinement and approval, customer/formula search, catalog administration, quantity previews, private product links, QR cards, copy-name action, reorder queue, optional SMTP and demo outbox.

Not included: payments, shipping integrations, automatic printing, native mobile apps, push notifications, offline support, inventory tracking, staff-specific roles, customer accounts, automated email retry queues, automated backups or production monitoring.

The default shared staff key is for local demonstration only. Before public launch, replace it with proper user authentication and permissions; use HTTPS, implement customer identity/consent and deletion policies, enforce formulation constraints, add abuse protection appropriate to expected traffic, configure backups and test recovery. There is basic request throttling and server-side validation, but this is not a production security audit.

## Editing guide

- `src/main.jsx`: React screens and user interactions.
- `src/styles.css`: colours, responsive layout, bottle illustration and card print styles.
- `server/index.js`: API routes, staff access, database persistence, QR and SMTP.
- `server/formula.js`: validation and the calculation helper.
- `prisma/schema.prisma`: database models.
- `prisma/seed.js`: default catalog and fictional demo customer.
- `vite.config.js`: frontend development server and API proxy.

The bottle artwork is CSS, so there are no image assets to download. Optional Google Fonts have local font fallbacks.
